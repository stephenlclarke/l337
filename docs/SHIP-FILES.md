# Ship definitions and generation

The schema and generation paths remain live. Predecessor calibration/name examples below describe their original implementation checkpoint; use [original hull bindings](player/ORIGINAL-FLEET.md) for current mission and player guidance. A generated catalogue or legacy fitting example does not activate an original replacement hull.

Every catalogue record lives in one authoritative, self-contained [TOML file](../Sources/L337Core/Resources/Ships), named by its stable `SHnnn` save ID. The folder contains 171 catalogue entries. Source presence does not mean a hull is flyable, purchasable or natively qualified. The current starting SH025 uses the same loader. SwiftPM copies the complete folder into the app resource bundle; development and packaged builds both decode it with pinned [TOMLDecoder 0.4.5](https://github.com/dduan/TOMLDecoder/tree/0.4.5). Invalid geometry, gameplay ranges, IDs or filenames fail loading explicitly. There is no separately maintained JSON catalogue or model pool.

Top-level fields retain identity, class, editions, evidence, model association and dimensional context. `[game]` contains authoritative native gameplay and price values; its absence means the object cannot be flown. `[design]` contains the actual vertices/faces, source and licence. Its inline `custody` table preserves original model hashes, source definition, components and archive/file dependencies. Original project designs also retain an authoring recipe. `[[profiles]]` retains every source/refit field, unit, status and basis; these are inspectable source facts and do not override `[game]`.

`[game].workTools` is an explicit list of `miningLaser` and/or `salvageCutter` utility capabilities. Current original R3 resources declare these per ID; missing data grants no work-tool capability. A capability installs no tool or purchase receipt. The actual fitted item and utility mount budget remain authoritative. Work tools are separate from Front/Left/Right/Rear combat facings. Mining requires a fitted Mining Laser and a physically verified rock hit; salvage requires actual paid equipment, lawful empty-section work and physical receiving.

Designs can optionally supply `materials`, an array of `{ name, colour, emissive }` records, and `faceMaterials`, one material index for each face. Colours are opaque RGBA integers. Missing materials retain the established hull lighting and colour. Incomplete assignments, out-of-range indices, unnamed materials and transparent faces fail validation. Materials survive normalisation and player mesh scaling; shaded views and generated portraits share the same lighting, while emissive panels keep their specified colour. White wireframe and tactical indicator colours remain independent of decorative materials. All 171 definitions now contain explicit authored palettes. `paletteName`, `appearanceSource`, `appearanceLicense` and `appearanceBasis` distinguish those native paint choices from historical geometry facts. Current originals retain their exact selected detailed/native source, palette, textures and UVs. Geometry replacement must preserve that source's origin, winding, material and void intent, with independent native qualification at the existing cap. The obsolete `hull-designs` and `liberator-design` Make targets are removed; their historical recipes cannot overwrite current resources through the shared writer.

Imported designs additionally retain `sourceFaceColours` (raw finite three-number source records), `sourceTextures` (`name`, `source`, `license`) and `sourceFaceTextures` (one `{ texture, uv }` mapping per face). Texture references use exact model basename/hash provenance; rights not established from the DAT are explicitly unknown. Geometry licences do not imply texture licences. Each UV entry has two finite numbers for each final face corner, reordered with any winding reversal and normalised by the source scale. UV tiling outside 0..1 is valid. An untextured face uses index -1 and an empty UV array. Unknown indices, incomplete face/corner assignments, absent provenance and nonfinite coordinates are rejected. Component assembly deduplicates and remaps references. Raw face triples from textured models may be grouping/placeholders, so they do not automatically become visible red/black hull colours.

Source texture names and UVs remain archival metadata. SH169 and SH170 now add separate authenticated `resolvedTextures` bindings for three selected, bundled Commies Ray diffuse images; [the texture contract](archive/checkpoints/SHIP-TEXTURES.md) records source rights, preparation, bounds and pending validation. No bitmap is fetched during play. Other ships retain actual mesh detail, opaque diffuse face colour and emissive panels; white wireframe and tactical inks remain independent. Diffuse sampling does not claim source normal/specular/emission shader fidelity. `make showroom-import` produces research staging data. It does not authorize copying historical geometry or balance into current original resources. Current resource changes require an exact source/R3 join and independent review.

See [the per-ship design review](archive/checkpoints/SHIP-DESIGNS.md) and [delivery checklist](archive/checkpoints/DELIVERY-BACKLOG.md) for the explicit review scope and acceptance status.

## Game conversion

Current mechanics, price, empty fitting and accommodation come from each exact [R3 contract](fleet-design-v2/ships) authenticated by [the fleet source manifest](milestones/FLEET-BACKLOG.json). They are authored game requirements, not historical measurements. The shared authoring writer validates current name, stable ID, family, origin, object kind and every bare mechanic before writing; it applies no historical balance overlay. Cargo is tonnes, fuel is native tenths of a light-year, jump is light-years and charge is seconds. Native work-tool capabilities do not install paid gear. Actual operating crew, purchased cabins, utility mounts, fuel and portable fittings remain separately owned and enforced.

Calibrated per-ID physical meshes retain source units and origin independently of normalized showroom previews. A resource or engineering estimate alone grants no native collision, flight, loaded mass, docking, population, acquisition or purchase authority. These joins and actual acceptance remain explicit fleet work. Capsules, stations, platforms and probes require their distinct domain owners.

The showroom compares both hulls with the same carried equipment and XYZZY policies. It uses the current hull as the initial baseline; pinning selects another hull with that same fit. Unlimited cargo is a policy, not an enormous numeric bay; the separate Fitted hold row keeps physical capacity comparable even in XYZZY. Fuel supply does not remove tank/navigation limits. Navigation computers increase the hull's base jump cap when their limit is greater; usable range is still limited by actual fuel. Green **BETTER**, orange **WORSE** and cyan **SAME** describe the selected value. Lower hull price and charging time are better; greater capacity/performance is better. Unknown values display `?`, not an equality claim. The displayed tenth-unit precision governs equality. Source mode retains original units and only subtracts compatible profiles.

## Economics and power sorting

Prices are the current per-ID R3 authored choices. The old Cobra-based cargo/price formula and research balance overlay are not current authoring inputs.

The actual editable result is the TOML `game.price` in credits. Commander accounts store tenths of a credit. Trade-in is 75% of the owned hull's current listed price; equipment transfers rather than being sold or credited. There is no free stock or refuel on exchange. The quote shows gross price, allowance, net cost/credit, resulting balance and compatibility before confirmation. Back is selected initially. Insufficient funds, oversized cargo (including reserved mission cargo), unsupported paid mounts/bay, excess fuel/missiles and incompatible active routes block the exchange without loss. Compatible mission state and property persist unchanged. XYZZY follows the same exchange rules; its existing cash policy is respected.

Power sorting uses the native standard hull index `energy + 2*shield + 32*recharge + 64*missilePylons + 128*laserMountCount`, strongest first. It is a project capability index, not a historical rating, installed weapon damage or crew count. Alphabetical sorting is A-Z; display name and stable ID break ties. Filters and selection survive sorting. Non-flyable objects follow ships in Power order.

## Update workflow

Review the exact current R3/source and native/physical changes on the fleet branch. The shared writer refuses stale values before modifying its destination. Reference generation requires all 171 resources to match current R3 identity and mechanics; remaining noncurrent objects fail explicitly, without granting pending hulls any native rights. G1 alone runs the actual generator, renderer and verification for the coherent fleet batch:

```sh
make ships
make ships-check
make ci
```

`make ships` reads the same folder as the game. It renders changed ships first, then generates [the central catalogue](SHIP-CATALOGUE.md) and [source/design appendix](SHIP-PROVENANCE.md). Each GIF has an explicit content-hash dependency on its entire TOML (including geometry), shared simulation/rendering Swift sources, pinned dependencies and render settings. The checked-in manifest also hashes the output, so missing/corrupt images rebuild. Unchanged inputs reuse their GIFs. A shared renderer change invalidates all affected animations. Paths and hashes contain no machine-specific absolute paths. `make ships-check` rejects stale GIFs or Markdown and runs in CI. `make showroom-data` is an alias of `make ships`.

The 256-square, 24-frame shaded animations use the actual game projection and renderer. They rotate once every 2.4 seconds and loop. The complete collection is about 12.7 MiB. README media still uses `make readme-media` exclusively.

`make showroom-import SHOWROOM_MODELS=... SHOWROOM_EXPANSIONS=... SHOWROOM_MODEL_CACHE=...` stages newly verified research output in ignored `reports/showroom-import`; it does not replace maintained TOMLs. Review source changes and update the selected TOML's source profiles/design/custody while preserving its game values and stable ID. The importer retains its source hash and full-assembly checks. Normal builds and media generation require no research checkout or source archive cache.
